# Design: Migrate developer tooling from npm to pnpm

## Technical Approach

Full switch (proposal Approach 1). Generate `pnpm-lock.yaml` from the existing `package-lock.json` with `pnpm import` so resolved versions are preserved, pin pnpm through corepack, then replace developer-facing npm commands with mechanical text edits. `src/` and every hexagonal layer are untouched; the `rules.design` domain-boundary rule is trivially satisfied.

## Architecture Decisions

| Topic                                                 | Options                                                                                | Tradeoff                                                                                            | Decision                                                                                                                          |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Version pin                                           | `packageManager` via `corepack use pnpm@10` / `engines.pnpm` / `only-allow` preinstall | `engines` is published metadata without enforcement; `only-allow` needs `npx` + network in a script | `packageManager: "pnpm@10.x.y+sha512..."` written by corepack; exact version recorded at apply                                    |
| Lockfile                                              | `pnpm import` / fresh `pnpm install`                                                   | Fresh install drifts within semver ranges                                                           | `pnpm import`; fresh install only as fallback, noted in PR                                                                        |
| Lifecycle scripts (pnpm 10 blocks dependency scripts) | Preemptive `pnpm.onlyBuiltDependencies` / add on demand                                | Preemptive allowlist widens trust without need                                                      | Add on demand: only if install lists an ignored build AND a verify command fails because of it. Root `prepare` (Husky) still runs |
| Hook runner                                           | `pnpm exec` / `pnpm dlx`                                                               | `dlx` downloads; `exec` is local-only like `npx --no`                                               | `pnpm exec`                                                                                                                       |
| smoke-pack                                            | Switch to pnpm / keep npm                                                              | Consumers install with npm/npx                                                                      | Keep npm (confirmed); update developer-facing text only                                                                           |
| `.prettierignore`                                     | Replace entry / keep both                                                              | lint-staged runs `prettier --write` on `*`, so an unignored lockfile is rewritten on commit         | Replace `package-lock.json` with `pnpm-lock.yaml`                                                                                 |

## Data Flow

    corepack enable ──> corepack pnpm@10 import ──> pnpm-lock.yaml
            │                                             │
            └─> corepack use pnpm@10 ──> packageManager ──┘──> pnpm install
                                                                  │
                                        prepare: husky ──> .husky hooks (pnpm exec/run)

Apply order matters: `corepack use` runs an install, so the lockfile is imported first and `corepack use` then installs against it.

## Interfaces / Contracts

```json
"packageManager": "pnpm@10.<minor>.<patch>+sha512.<hash>"
```

No runtime interfaces change; the published tarball contents (`files`) are unaffected.

## Testing Strategy

No new automated tests (tooling only; strict TDD has no code under change). Verification is command-based:

| Layer        | What                        | Approach                                                                                                                                |
| ------------ | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Install      | Clean install from lockfile | `rm -rf node_modules && pnpm install --frozen-lockfile`; inspect "Ignored build scripts" warning; `.husky/_` exists                     |
| Phantom deps | Strict layout resolution    | `pnpm run typecheck`, `pnpm test`, `pnpm run build` (runs `check-dist-aliases.mjs`), `pnpm exec commitlint --help`                      |
| Hooks        | Block bad input             | `echo "bad" \| pnpm exec commitlint` fails; commit with misformatted staged file gets formatted; `git push --dry-run` triggers pre-push |
| Pack         | Consumer path               | `pnpm run smoke:pack` passes                                                                                                            |
| Format       | Ignore list                 | `pnpm run format:check` passes; lockfile not reported                                                                                   |
| Residue      | No dev npm commands         | `rg -n 'npm (run\|install\|test)\|npx --no' README.md .husky package.json openspec/config.yaml scripts` shows only smoke-pack logic     |

Phantom-dependency failures are fixed by adding the missing package as an explicit devDependency, never by `shamefully-hoist`.

## Threat Matrix

N/A — no routing, subprocess, VCS/PR automation, or executable-file classification boundary changes. Hook scripts swap one local-bin runner for another (`npx --no` -> `pnpm exec`), both local-only with fixed argv; smoke-pack subprocess logic is unchanged.

## Migration / Rollout

Contributors: `corepack enable`, then `pnpm install` (corepack fetches the pinned version). Existing clones: `rm -rf node_modules` first to avoid the mixed npm layout. Without corepack, `npm i -g pnpm@10` works; `npm install` is not blocked but unsupported (README states this).

Rollback: revert the PR (restores `package-lock.json` and npm commands), then `rm -rf node_modules && npm install`.
